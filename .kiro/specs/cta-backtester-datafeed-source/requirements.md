# 需求 — CTA 回测行情数据下载源选择

## 引言

当前 CTA 回测窗口的「下载数据」功能使用应用初始化时的全局 datafeed，并且在 K 线数据下载时会优先尝试合约所属网关的历史数据接口。用户需要在页面上直接选择本次下载使用的行情数据源，并支持通过下拉框选择或手动输入数据源名称。

本 spec 面向当前本地 Python 环境中的 `vnpy_ctabacktester` 应用包。

## 需求

### 需求 1 — 页面增加行情数据下载源选择

**用户故事：** 作为 CTA 回测用户，我希望在交易策略参数区域看到行情数据下载源选择项，以便下载数据前明确指定数据来源。

#### 验收标准

1. 当用户打开 CTA 回测窗口时，交易策略下方应显示「行情数据源」输入控件。
2. 该控件应为可编辑下拉框，既能从已有选项选择，也能直接输入数据源名称。
3. 下拉选项应包含当前全局配置中的 `datafeed.name`，并包含常用 vn.py 数据源名称。
4. 下拉选项应包含本地支持的虚拟币行情源，例如 `binance_spot`、`binance_usdt_futures` 等。

### 需求 2 — 下载数据使用页面选择的数据源

**用户故事：** 作为 CTA 回测用户，我希望点击「下载数据」后，程序从我选择的数据源直接获取本地代码对应的历史数据。

#### 验收标准

1. 当用户点击「下载数据」时，UI 应将当前行情数据源名称传入回测引擎。
2. 回测引擎应按该名称创建并初始化 datafeed，再查询历史 K 线或 Tick。
3. K 线下载不应再优先走合约网关历史数据接口；应直接使用选择的数据源。
4. 如果数据源为空、未安装、初始化失败或查询失败，应输出清晰日志并结束本次任务。

### 需求 5 — 支持虚拟币行情源

**用户故事：** 作为虚拟币策略用户，我希望能在 CTA 回测页面直接选择虚拟币行情源，以便下载 BTCUSDT、ETHUSDT 等合约的历史 K 线。

#### 验收标准

1. 当用户选择虚拟币行情源名称时，回测引擎应识别该名称为 crypto gateway，而不是普通 `vnpy_<name>` datafeed。
2. 下载 K 线数据时，应通过对应虚拟币网关的 `query_history` 直接获取历史数据并保存到数据库。
3. 如果本地代码的交易所后缀与所选虚拟币网关不匹配，应输出清晰日志并结束本次任务。
4. 虚拟币行情源暂不支持 Tick 下载时，应输出清晰日志。

### 需求 6 — 本地代码支持来源选择和下拉输入

**用户故事：** 作为 CTA 回测用户，我希望切换行情数据源后，可以选择本地代码列表是从数据源重新加载，还是从本地已有数据/合约加载，并且仍然可以手动输入代码。

#### 验收标准

1. 「本地代码」控件应为可编辑下拉框，用户既能选择已有选项，也能直接输入 `vt_symbol`。
2. 页面应提供本地代码来源选择，至少包含「本地」和「数据源Reload」两种方式。
3. 当选择「本地」并刷新时，应从本地数据库已有 K 线/Tick 概览和当前 MainEngine 合约列表中加载 `vt_symbol`。
4. 当选择「数据源Reload」并刷新时，应按当前行情数据源尝试加载代码列表；虚拟币行情源应从对应网关合约接口加载。
5. 当当前行情数据源不支持代码列表加载时，应输出清晰日志，用户仍可手动输入本地代码。

### 需求 7 — 网络异常不弹出全局异常窗口

**用户故事：** 作为 CTA 回测用户，我希望数据源 Reload 或下载遇到网络超时时只在日志里提示，而不是弹出阻塞性的 Qt 异常窗口。

#### 验收标准

1. 当虚拟币行情源合约列表 Reload 发生连接超时、代理失败或 HTTP 错误时，应在日志面板输出失败原因并返回空列表。
2. Reload 逻辑不应调用旧 REST 客户端默认 `sys.excepthook` 路径。
3. UI 刷新本地代码候选项时应有外层异常兜底，避免任何数据源异常冒泡到 Qt 全局异常处理。

### 需求 8 — K 线周期支持来源选择和同步

**用户故事：** 作为 CTA 回测用户，我希望 K 线周期也能根据当前行情数据源/交易所同步可用选项，并且仍然可以手动输入。

#### 验收标准

1. 「K线周期」控件应为可编辑下拉框，用户既能选择已有选项，也能直接输入周期值。
2. 页面应提供周期来源选择，至少包含「本地」和「数据源Reload」两种方式。
3. 当选择「本地」并刷新时，应从本地数据库已有 K 线概览中加载该本地代码可用周期；若无本地数据，应回退到 vn.py 默认周期。
4. 当选择「数据源Reload」并刷新时，应按当前行情数据源加载当前实现支持的周期；虚拟币行情源应从对应交易所映射加载。
5. 当数据源支持的交易所周期多于当前回测下载实现可处理的周期时，应只展示当前可安全下载/回测的周期。

### 需求 3 — 保存与恢复设置

**用户故事：** 作为经常使用同一数据源的用户，我希望上次选择的数据源能在下次打开窗口时恢复。

#### 验收标准

1. 当用户启动回测或下载数据时，应保存当前行情数据源名称到现有 CTA 回测设置文件。
2. 当用户再次打开 CTA 回测窗口时，应恢复保存的数据源名称。
3. 保存逻辑不得破坏既有策略、合约、周期、日期和交易参数的恢复。

### 需求 4 — 验证

**用户故事：** 作为维护者，我希望改动至少通过静态导入和语法验证，以降低修改安装包 UI 代码带来的风险。

#### 验收标准

1. 修改后的 `vnpy_ctabacktester.engine` 和 `vnpy_ctabacktester.ui.widget` 应能被当前 Python 环境成功导入。
2. 修改后的文件应通过 `compileall` 语法检查。
